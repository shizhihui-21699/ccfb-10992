# 无源码二进制热补丁：recvfrom 栈溢出（arm64 macOS / Mach-O）

模拟场景：车间老设备控制程序由外包在十余年前编写、源码已丢失、厂家已不存在。
审计发现其网络读取函数把 `recvfrom` 的长度参数设成远端可控的 512，而栈缓冲区只有
64 字节，且**完全没有长度检查**——经典栈缓冲区溢出。本项目在**没有源码**的前提下：

1. 用 Rust 写一个二进制热补丁工具，静态定位出问题的函数调用点；
2. 把长度检查的补丁代码写进可执行文件的空闲区（code cave），并改写一条跳转；
3. 保证打补丁后的程序除“超长读取被钳制”外，其它功能与原版逐字节等价；
4. 提供能稳定触发溢出的攻击测试，证明原版会崩、补丁版被阻断。

> 平台：arm64（Apple Silicon）macOS，目标格式 Mach-O `MH_EXECUTE`。
> 选 arm64 macOS 是因为它强制代码签名，正好覆盖“改完必须重签”这一真实约束。

## 漏洞本身

`vuln_udp_server.c` 的 `handle_packet()`：

```c
char buf[64];                       // 栈缓冲区只有 64 字节
recvfrom(sockfd, buf, 512, ...);    // 长度参数 512，无任何检查
```

反编译/反汇编后在 `0x100000800` 看到紧邻调用的两条指令：

```asm
mov  x2, #0x200          ; 512，recvfrom 的长度参数（失控）
bl   _recvfrom
```

## 无源码如何定位

工具不依赖函数名或符号表（对 `strip -x` 剥离过的二进制同样有效），只凭两点：

1. **导入表解析**：通过 `LC_DYSYMTAB` 的间接符号表，把 `__stubs` 节里每个 stub
   入口解析成导入符号名，得到 `_recvfrom` stub 的虚拟地址；
2. **指令签名扫描**：在所有可执行节区里匹配
   `MOVZ Xd,#imm16`（64 位立即数装载）后紧跟 `BL <recvfrom stub>` 的模式，
   且立即数明显大于正常栈缓冲——命中即缺陷点。

实测对剥离符号后的二进制，仍能准确报出
`hook=0x100000800 ... 失控长度=512 ... 位于 _handle_packet+0x54`。

## 补丁插入方式（选稳妥的一种：code cave + 单点跳转）

采用业界热补丁常用的 **code cave（代码洞穴）** 方案，而不是内联扩函数或搬移节区：

- **不移动任何节区、不改 load command、不改变补丁本身的文件长度**，dyld 绑定、
  Objective-C 元数据、其它函数的偏移全部不受影响；
- 只写两个地方：
  1. 可执行的空闲洞穴 `__TEXT,__patchcave`（样例中预留的 256 字节全 0、不可达区域，
     模拟老固件里函数对齐填充/废弃函数留下的空间；工具也支持在可执行节区自动找
     全 0 对齐空洞作为回退）；
  2. 缺陷点那**一条** 4 字节指令，原地改成 `B` 跳进洞穴；
- 桩只借用 AAPCS64 的过程内临时寄存器 `x16/x17`（IP0/IP1，调用边界不保证保留），
  并在桩内重建被替换指令的效果，返回后寄存器状态与原执行流完全一致。

补丁桩（5 条指令，20 字节）逻辑——先做长度检查再继续原来的读取：

```asm
mov  x16, x2          ; 保存原始长度（512）
cmp  x16, #63         ; 与安全容量比较（64 字节字符串缓冲，留 1 字节给 NUL）
b.ls <keep>           ; 原始长度 <= 63：保持原值，跳过钳制
mov  x2, #63          ; 否则：把 recvfrom 的长度参数钳到 63
keep:
b    <原 bl 处>        ; 回到 recvfrom 调用，后续代码原封不动
```

钳制而非直接丢弃整个报文：`recvfrom` 最多收 63 字节，数据报超长部分由内核丢弃，
语义等价于“先检查长度，超长不收”，对上层业务零侵入。

> **为什么默认是 63 不是 64**：该缓冲按 C 字符串使用（后面有 `%s`/`strncmp`）。
> 若钳到 64 会写满整个缓冲、没有 NUL 终止符，导致字符串函数越界读——这是首轮测试
> 真实暴露出来的问题。`--cap` 可覆盖；非字符串的裸字节缓冲可用满整个容量。

### arm64 macOS 的签名约束

修改 `__TEXT` 后内嵌代码签名立即失效，内核会拒绝执行。工具在写入后自动执行
`codesign --force --sign -` 重新 ad-hoc 签名（可用 `--no-codesign` 关闭）。
重签会重写 `__LINKEDIT` 末尾的签名块、使文件变长——**这是签名工具的产物，不是补丁
写入造成的**。用 `--no-codesign` 产出的副本与原版**逐字节等长**，且全部差异仅落在
钩子 4 字节与洞穴 64 字节内，区间外改动为 0。

## 用法

```bash
# 一键复现
./run_all.sh

# 或分步
cargo build --release --manifest-path hotpatch/Cargo.toml
HP=hotpatch/target/release/hotpatch

$HP info   vuln_app/vuln_udp_server            # 只读分析 + 缺陷点扫描
$HP patch  vuln_app/vuln_udp_server -o out.bin # 打补丁（默认 cap=63，自动备份+重签）
$HP verify out.bin                             # 安装完整性/跳转/逐节区比对校验

# 可选参数
#   --cap N         自定义钳制上限（1..=4095）
#   --no-backup     不生成 .orig 备份
#   --no-codesign   跳过重签（产物等长，但 arm64 macOS 上需另行签名才能运行）
```

`patch` 原地改写时会先备份成 `<bin>.orig`；`verify` 会优先找 `.orig`、否则去掉
`.patched` 后缀定位原始文件做逐节区比对。洞穴头部写入 `HPC1` 魔数与元数据
（原始指令、cap、钩子/stub/返回地址），防止重复打补丁并支持回溯校验。

## 测试结果

- **原版**：300 字节 UDP 攻击下稳定栈溢出，进程直接崩溃（或触发栈哨兵告警）；
- **补丁版**：同样攻击被钳为 63 字节回显，无哨兵告警、进程存活、攻击后服务照常；
- **等价性**：长度 1..63 的安全报文，两版应答**逐字节一致**，STATUS 统计一致；
  长度 63/64/65/128/300/511/512 在补丁版上全部安全处理为最多 63 字节；
- **外科手术性**：补丁写入等长，差异仅钩子 4 字节 + 洞穴；`verify` 逐节区确认
  其它节区零改动；
- **抗剥离**：对 `strip -x` 后的二进制仍能定位并成功打补丁、通过攻击测试。

## 适用范围与局限（如实说明）

- 仅实现 arm64 Mach-O `MH_EXECUTE`；x86_64、ELF/PE、fat binary、PAGEZERO 收紧的
  新版本布局未覆盖（架构上按“解析器 + 指令编码器”分层，移植需替换这两层）；
- 定位签名针对“`MOVZ` 立即数 + `BL recvfrom`”这一具体模式（对应 -O0 风格）。
  高优化级别下长度可能来自寄存器/内存，需要扩展模式库；多命中时工具拒绝盲改并报错；
- 钳制语义适用于“超长部分可安全丢弃”的 UDP 报文；TCP 流场景应改为先收长度头再决定，
  不能简单截断；
- 真实生产固件往往没有现成的可执行洞穴，回退策略会在可执行节区找全 0 对齐空洞；
  若完全没有空间，则需要新增段（会改变文件结构，本工具刻意不做以保持稳妥）。
